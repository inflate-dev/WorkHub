# 仕様書01: WorkHub — 社内業務アプリ基盤(Phase 1)

## Context

企業向けに横展開できる業務アプリのベースを作る。想定業種は水道工事・住宅設備業(例: 便器/給湯器/給水設備の交換工事)。最終形の機能、優先度順:
1. **顧客向けセルフ見積**(①便器交換/修理、③給湯器・エコキュート交換、④給水設備の部品交換について、顧客自身が型番/グレードを選ぶだけで見積が完成し、そのまま申し込める)+ その申込みを受け取る**社員向け見積管理**(表裏一体の機能)
2. 社内情報(Google Drive/Docs)を参照して答える社内AIチャット
3. 社内コミュニケーション(優先度低・後回し)

**②(給水管の分水・引込工事)は今回のスコープ外。** 土工・道路占用・水道局申請要否など現場条件で数量が大きく変わり、写真や図面だけでは正確な積算ができないため、簡易見積・セルフ見積のどちらにも向かない。将来「概算レンジ表示+現地調査予約」のような別フローとして検討する。

ユーザーとの事前すり合わせで下記の基盤方針が確定した:
- **展開方式**: 1コードベースをテンプレートとして、企業ごとに個別デプロイ(Vercelプロジェクト+Supabaseプロジェクトを企業ごとに用意)。マルチテナントDB分離は不要。
- **社内AIのデータ源**: Google Workspace(Drive/Docs)
- **インフラ**: Vercel + Supabase(Postgres/Auth/Storage)
- **LLM**: OpenAI API(社内AIチャットの回答生成、および見積内の消耗品費用のWeb検索にResponses APIのweb_search機能を使用)

リポジトリは現状空(gitのみ初期化済み)。このPhase 1では「ベースの土台」を作る: プロジェクト雛形、認証、ブランディング設定の仕組み、そして最優先機能の**顧客向けセルフ見積+社員向け見積管理**を一気通貫で動く状態にする。社内AI・社内コミュニケーションは次フェーズ以降で個別に設計・実装する(本フェーズではDBスキーマ含め着手しない。テーブル追加は将来のマイグレーションで対応)。Phase 1は「顧客向けセルフ見積」のみ公開(未認証)ルートを持ち、それ以外(見積管理・品目マスタ・設定)は社員向け認証必須エリアとする。

## 技術スタック

- Next.js 14(App Router) + TypeScript
- Tailwind CSS + shadcn/ui(企業ごとの配色・ロゴ差し替えがしやすいコンポーネント基盤)
- Supabase(Postgres + Auth + Storage)、スキーマは Supabase CLI のマイグレーションファイルで管理
- 認証: Supabase Auth の Google OAuth(社員は自社Google Workspaceアカウントでログイン。顧客向けフォームは認証不要)
- メール通知: Resend(見積作成時の社長宛通知に使用)
- デプロイ: Vercel(Node 20 / npm を使用。pnpmは未インストールのため npm で統一)

## 顧客向けセルフ見積(①③④)の仕様

### 対象カテゴリと明細構成

| カテゴリ | 内容 | 標準的な明細行 |
|---|---|---|
| ① 便器交換/修理 | 洋式トイレの便器本体交換(配管位置は変わらない前提) | 便器本体(型番/グレード)、ウォシュレット、衛生器具取替工費、既設便器処分費、消耗品・雑材料費 |
| ③ 給湯器・エコキュート交換 | 同型式への単純入替(設置場所変更や配管引き直しは対象外) | 機器代、設置費、既設撤去処分費、配管接続費、消耗品・雑材料費 |
| ④ 給水設備の部品交換 | ポンプ・タンク・バルブ等、同じ場所への同型部品の入替(井戸ポンプ本体など機種選定が必要なものは対象外) | 部品代(型番/グレード)、交換工費、既設処分費、消耗品・雑材料費 |

いずれも「グレードを選べば金額が決まる」定型パターンのため、顧客が自分で型番を調べる必要はなく、**少数のグレード選択**(例: エコノミー/スタンダード/プレミアムの3段階)から選ぶ形にする。メーカー・型番を1件ずつ選ぶ詳細UIは今回は採用しない(価格マスタの登録・保守コストが高いため)。

### 金額の算出方法

- 便器本体/ウォシュレット/機器代/部品代/各種工費/処分費は、グレードごとに**事前登録した固定価格**(後述の`grade_options`/`catalog_items`)から組み立てる。市況で大きく変動しないため固定でよい。
- **消費品・雑材料費のみ**、見積作成のタイミングでOpenAI Responses APIの`web_search`ツールを使って現在の市場価格を検索し、金額を算出する(例: 「トイレ交換工事に伴う消耗品・雑材料(シールテープ、給水フレキ管、コーキング材等)の標準的な費用相場」を検索させ、金額レンジの目安を取得)。
  - 検索には数秒かかるため、見積表示前に「消耗品費用を確認しています…」というローディング状態を挟む
  - API呼び出しが失敗・タイムアウトした場合は、`catalog_items`にあらかじめ登録した**フォールバック価格**を使用し、見積作成自体は止めない
  - 検索結果の根拠(サマリー・参照元)は`quote_items.ai_search_note`に保存し、社員が後から金額の妥当性を確認できるようにする

### 顧客フロー

1. `/estimate` でカテゴリ選択(①③④のカード)
2. `/estimate/[category]` でグレード選択 → 選択した瞬間に上記ロジックで自動計算し、明細+合計金額を表示
3. 「この内容で申し込む」ボタン → `/estimate/[category]/apply` で氏名・住所・電話番号・メールアドレス・希望工事日を入力
4. 送信 → `/api/estimate/submit` がバリデーション後、service roleクライアントで`quotes`(`source: customer_self_service`, `status: requested`)+`quote_items`を作成し、既存の見積作成通知(Resend)を`company_config.notify_email`宛に送信
5. `/estimate/[category]/complete` で申込み完了を表示(「担当者より改めてご連絡します」等)

社員は見積管理側の`/quotes`一覧に`requested`ステータスの見積として表示され、内容を確認したうえで通常の見積と同様にステータスを更新(`draft`→`sent`→`accepted`等)していく。**顧客からの申込みも社員が手動作成する見積も、同じ`quotes`/`quote_items`に集約する**ことで、見積管理側の実装(Phase 1で先に固めた設計)をそのまま再利用する。

## DBスキーマ(`supabase/migrations/0001_init.sql`)

- `company_config`(1行のみ運用): `id`, `name`, `logo_url`, `primary_color`, `contact_email`, `notify_email`(見積作成時の通知先。社長のメールアドレス), `quote_number_prefix`(default `'Q'`), `quote_number_next`(default `1`), `updated_at`
  - RLS: 認証済み社員はSELECT可、UPDATEはadmin roleのみ
- `profiles`(社員): `id`(auth.usersのidと同一), `full_name`, `role`(`admin` | `employee`), `created_at`
  - RLS: 本人はSELECT可、admin roleは全件SELECT/UPDATE可
- `item_master`(単価マスタ/品目マスタ): `id`, `name`, `default_unit`(text, default `'式'`), `default_unit_price`(numeric), `category`(text, nullable), `created_at`, `updated_at`
  - RLS: 認証済み社員はSELECT可、INSERT/UPDATE/DELETEはadmin roleのみ(マスタの整合性を保つため登録・編集は管理者に限定)
- `quotes`(見積): `id`, `quote_number`(unique、例 `Q-2026-0001`)、`source`(`internal`/`customer_self_service`、default `internal`), `category`(`toilet`/`water_heater`/`water_parts`、nullable。セルフ見積由来のみ設定), `grade_option_id`(`grade_options`への nullable FK), `customer_name`, `customer_company`, `customer_email`, `customer_phone`, `customer_address`(nullable。セルフ見積の申込みで使用), `preferred_date`(nullable。希望工事日), `status`(`requested`/`draft`/`sent`/`accepted`/`rejected`、default `draft`), `issue_date`(default 今日), `valid_until`, `notes`, `subtotal`(明細行合計、税・バッファー適用前), `buffer_rate`(numeric, default `1.0`。1.1倍・1.2倍などのバッファーを入力), `buffered_subtotal`(`subtotal * buffer_rate`), `tax_rate`(default `0.10`), `tax_amount`(`buffered_subtotal * tax_rate`), `total`(`buffered_subtotal + tax_amount`), `created_by`(`profiles`への nullable FK。顧客セルフ見積の場合は `null`), `created_at`, `updated_at`
  - `status`の`requested`は顧客がセルフ見積フォームから申し込んだ直後の状態(社員未確認)。社員が手動作成する見積は`draft`から開始する
  - `subtotal`/`buffered_subtotal`/`tax_amount`/`total` は明細行の増減や税率変更に応じてアプリ側(保存時)で再計算してから書き込む(`quotes`だけでは子テーブル`quote_items`の合計をDB生成列にできないため)
  - 消費税は外税方式(小計・バッファー適用後の金額に対して税を加算)を採用。内税や軽減税率の考慮は将来の検討事項とする
  - RLS: 認証済み社員は全件SELECT/INSERT/UPDATE可(小規模チーム運用を想定し、作成者以外の社員も編集可とする。将来必要なら作成者+adminに絞る)。匿名からのSELECT/UPDATEは不可。INSERTは`/api/estimate/submit`がservice roleクライアントで行う
- `quote_items`(見積明細): `id`, `quote_id`(FK, `on delete cascade`), `item_id`(`item_master`への nullable FK、`on delete set null`), `source`(`manual`/`catalog`/`ai_search`、default `manual`), `ai_search_note`(text, nullable。`ai_search`行の検索結果サマリー・参照元), `sort_order`, `description`, `quantity`(numeric, default `1`), `unit`(text, default `'式'`), `unit_price`(numeric), `amount`(numeric、生成列 `quantity * unit_price`)
  - `item_id` が設定されている行は品目マスタから選択して追加された明細(選択時に`description`/`unit`/`unit_price`をマスタ値で初期化し、その後は自由に上書き可能)。`source: catalog`は`catalog_items`由来の固定明細、`source: ai_search`はConsumables検索由来の明細
  - RLS: 親`quotes`にアクセスできる社員のみ。匿名からのSELECT/INSERT/UPDATEは不可(`/api/estimate/submit`がservice roleクライアントで作成)
- `grade_options`(セルフ見積のグレード選択肢マスタ): `id`, `category`(`toilet`/`water_heater`/`water_parts`), `subcategory`(text, nullable。④のポンプ/バルブ/タンク等の種別), `grade_key`(text、例 `standard`), `label`(表示名、例 `スタンダード`), `description`(text, nullable), `fallback_consumables_price`(numeric。AI検索失敗時に使う消耗品費のフォールバック額), `sort_order`, `is_active`(default `true`), `created_at`, `updated_at`
  - RLS: 誰でもSELECT可(顧客向け画面で表示するため匿名アクセスを許可)、INSERT/UPDATE/DELETEはadmin roleのみ
- `catalog_items`(グレードごとの固定明細行テンプレート): `id`, `grade_option_id`(FK, `on delete cascade`), `description`, `unit`(default `'式'`), `unit_price`(numeric), `sort_order`
  - 見積作成時にこの内容をコピーして`quote_items`(`source: catalog`)を生成する。消耗品・雑材料費の行はここには含めず、都度AI検索で生成する
  - RLS: 誰でもSELECT可(匿名アクセス許可)、INSERT/UPDATE/DELETEはadmin roleのみ
- 採番用関数 `next_quote_number()`: `company_config.quote_number_next` を行ロックしながら取得・インクリメントし、`{prefix}-{年}-{4桁連番}` 形式の文字列を返すPostgres関数。見積新規作成時にアプリからRPCで呼び出し、採番の競合を防ぐ

将来テーブル(本Phaseでは作らない、README/コメントで明記のみ): `documents`, `document_chunks`(pgvector、社内AI RAG用)、`chat_sessions`, `chat_messages`(社内AIチャット履歴)。②(給水管の分水・引込工事)向けの現地調査予約関連テーブルは、②に着手する際に別途設計する。

## 実装ステップ

1. **プロジェクト雛形**: `create-next-app`(TypeScript, App Router, Tailwind, ESLint)→ shadcn/ui初期化 → Supabase CLI初期化(`supabase init`)
2. **Supabaseクライアント層**: `@supabase/ssr` を使い `lib/supabase/{client,server,middleware}.ts` を実装。ルート `middleware.ts` で `/(app)/*` を未認証なら `/auth/login` にリダイレクト
3. **マイグレーション**: `0001_init.sql` を作成(`company_config`, `profiles`, `item_master`, `grade_options`, `catalog_items`, `quotes`, `quote_items` + RLSポリシー + `next_quote_number()` 関数)
4. **認証**: `/auth/login` にGoogleログインボタン、`/auth/callback/route.ts` でコード交換。初回ログイン時に `profiles` へ自動upsert(role defaultは `employee`)
5. **ブランディング層**: `lib/config/branding.ts` が `company_config` を取得し、無ければ `.env` の `NEXT_PUBLIC_DEFAULT_*` にフォールバック。ルートlayoutでCSS変数(`--brand-primary` 等)に注入
6. **品目マスタ管理**(`/admin/items`): 品目の一覧・登録・編集(admin roleのみ)。`name` / `default_unit` / `default_unit_price` / `category` を管理
7. **セルフ見積カタログ管理**(`/admin/catalog`): カテゴリ(①③④)ごとの`grade_options`(グレード)と、その`catalog_items`(固定明細行)を登録・編集(admin roleのみ)。初期データ(①③④それぞれ3グレード程度)はマイグレーションのseedとして投入する
8. **消耗品費用の検索**(`lib/ai/estimate-consumables.ts` → `/api/estimate/consumables`): OpenAI Responses APIを`web_search`ツール付きで呼び出し、カテゴリに応じた消耗品・雑材料費の相場を検索。金額をパースして返す。失敗・タイムアウト時は`grade_options.fallback_consumables_price`を返す
9. **顧客向けセルフ見積画面**(`/estimate`, `/estimate/[category]`): カテゴリ選択→グレード選択→選択した瞬間に`catalog_items`+消耗品費(手順8のAPI)を組み合わせて明細・合計をリアルタイム表示
10. **申込みフォーム・送信**(`/estimate/[category]/apply`, `/api/estimate/submit`): 氏名・住所・電話番号・メールアドレス・希望工事日を入力→バリデーション→service roleクライアントで`quotes`(`source: customer_self_service`, `status: requested`)+`quote_items`をinsert→Resendで通知メール送信→`/estimate/[category]/complete`へ遷移
11. **見積フォーム(社員向け)**(`/quotes/new`, `/quotes/[id]`): 顧客情報(氏名・会社名・連絡先)入力+明細行の動的追加/削除。明細行は品目マスタから選択(`item-picker.tsx`)または自由入力。数量×単価で行金額を自動計算し、小計→バッファー倍率(既定値`1.0`)適用後金額→消費税(外税)→合計をリアルタイム計算
12. **見積保存**: 新規作成時は `next_quote_number()` をRPC呼び出しして採番→insert→Resendで `company_config.notify_email` 宛に見積作成通知メールを送信。更新時はステータス変更(requested/draft/sent/accepted/rejected)も可能に
13. **見積一覧**(`/quotes`): ステータス・顧客名・source(顧客申込み/社員作成)で絞り込み、一覧から詳細へ遷移
14. **印刷ビュー**(`/quotes/[id]/print`): `company_config` のロゴ・社名・連絡先を表示したA4向けレイアウト。ブラウザの印刷機能でPDF保存する運用とし、サーバーサイドPDF生成ライブラリはPhase1では導入しない
15. **admin設定画面**: `/admin/settings` で会社名・ロゴURL・配色・見積番号プレフィックス・通知先メールアドレス(`notify_email`)を編集(admin roleのみアクセス可)
16. **README**: セットアップ手順(Supabaseプロジェクト作成、Google OAuth設定、Resend APIキー取得、OpenAI APIキー取得、`.env`一覧)と「新規企業向けにフォークしてカスタマイズする手順」を記載

## 検証方法
